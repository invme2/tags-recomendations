# Architecture Decision Records

Формат: ADR (контекст → решение → альтернативы → последствия). Каждое
архитектурное решение — отдельная запись. Не редактируем старые ADR; если
решение пересматривается — пишем новый ADR со ссылкой «supersedes ADR-XXX».

---

## ADR-001: Моно-репо для taxonomy и pipeline, имя `invme2/tags-recomendations`
**Дата:** 2026-05-05
**Статус:** Accepted

**Контекст.** Taxonomy и Shopify-пайплайн логически связаны: пайплайн
потребляет taxonomy. При этом taxonomy эволюционирует чаще и имеет
собственный CI (валидация схемы), а пайплайн — это `.ipynb` с особыми
правилами правок. На bootstrap-сессии возникал вопрос: оставить имя репо
`invme2/tags-recomendations` (текущий remote) или мигрировать в
`wanelo-shopify-system` (как фигурирует в исходном промпте).

**Решение.** Один репозиторий, две независимые подпапки `taxonomy/` и
`pipeline/`, общий тулинг в `tools/`, общий слой памяти (`CLAUDE.md` и др.) в
корне. Имя репо зафиксировано — **`invme2/tags-recomendations`** (подтверждено
пользователем 2026-05-05). Никакой миграции не планируется.

**Альтернативы.**
- Два отдельных репо: лишняя ceremony при кросс-изменениях, дублирование
  memory-файлов.
- Git submodule для taxonomy: усложняет workflow, плохо дружит с raw-URL.
- Переименование в `wanelo-shopify-system`: разорвало бы существующий remote
  и raw-URL ссылки; пользователь решил сохранить текущее имя.

**Последствия.** Один CHANGELOG на оба продукта, но раздельные CI-workflow.
Pipeline ссылается на taxonomy через raw-URL вида
`https://raw.githubusercontent.com/invme2/tags-recomendations/<ref>/taxonomy/taxonomy.json`.

## ADR-002: JSON Schema (Draft-07) для валидации taxonomy
**Дата:** 2026-05-05
**Статус:** Accepted

**Контекст.** Taxonomy — массив ~765 кластеров со сложной структурой
(`personas`, `intents`, `demos`, `related`, `embed_text`). Ручные правки и
автогенерация Claude API могут поломать структуру.

**Решение.** Описать схему в `taxonomy/schema.json` (Draft-07) и валидировать
библиотекой `jsonschema`. Сверх схемы — три бизнес-проверки в коде:
дубли `tag`, ссылочная целостность `related[]`, непустой `embed_text`.

**Альтернативы.**
- Pydantic-модель: дороже в поддержке, требует синхронизации с CI на других языках.
- Только runtime-проверки в коде: непереносимо в редакторы / IDE-подсказки.

**Последствия.** Любая правка `taxonomy.json` обязана пройти `validate_taxonomy.py`
до коммита. CI блокирует merge при невалидной схеме.

## ADR-003: `nbformat` как единственный путь правок ноутбука
**Дата:** 2026-05-05
**Статус:** Accepted

**Контекст.** Jupyter-ноутбук — это JSON с глобальным state по ячейкам.
Прямые правки руками или regex по сырому JSON ломают `cell_id`, метаданные,
порядок ячеек и git-diff.

**Решение.** Все правки `.ipynb` идут через `pipeline/tools/apply_patch.py`,
который использует `nbformat.read` → точечный `str.replace` в исходнике
конкретной ячейки → `nbformat.validate` → `nbformat.write`. Никаких ручных
правок JSON.

**Альтернативы.**
- `jupytext` (sync с `.py`): требует двунаправленной синхронизации, риск
  расхождения, ломает workflow в Colab.
- Плагины IDE: не воспроизводимо в CI.

**Последствия.** Каждая правка ноутбука документируется в `pipeline/PATCHES.md`
(какая ячейка, что было, что стало, зачем). Перед правкой — snapshot в
`pipeline/.snapshots/`.

## ADR-004: Memory-файлы в корне репо как контракт между сессиями
**Дата:** 2026-05-05
**Статус:** Accepted

**Контекст.** Между сессиями Claude теряет контекст. Прошлая сессия могла
выбрать метод X; следующая, не зная этого, выберет Y и сломает совместимость.

**Решение.** Четыре файла в корне:
- `CLAUDE.md` — конституция, читается ПЕРВОЙ в каждой сессии.
- `DECISIONS.md` — этот файл, ADR.
- `CHANGELOG.md` — хроника изменений (Keep a Changelog).
- `TROUBLESHOOTING.md` — известные проблемы и фиксы.

Язык повествования — русский (язык пользователя), технические идентификаторы
и команды — английский.

**Альтернативы.**
- Wiki в GitHub: не приходит в репо, не виден в `git log`.
- Issues/Discussions: эфемерны, плохо линкуются на конкретный код.

**Последствия.** Любая сессия начинается с чтения `CLAUDE.md` и заканчивается
обновлением соответствующих файлов перед коммитом.

## ADR-005: Schema для taxonomy на старте — черновая, до доставки источника
**Дата:** 2026-05-05
**Статус:** Provisional (требует ревизии после доставки `taxonomy.json`)

**Контекст.** На момент bootstrap-сессии оригинальный `taxonomy.json`
пользователя недоступен (Windows-temp путь, Linux-окружение Claude его не
видит). Тем не менее структура моно-репо и валидатор должны существовать,
чтобы CI работал с первого коммита.

**Решение.** Написать черновую `schema.json` по описанию из bootstrap-промпта:
обязательные поля кластера — `tag`, `embed_text`; опциональные —
`personas`, `intents`, `demos`, `related`. Master-списки `personas`, `intents`,
`demos` на верхнем уровне. `additionalProperties: true` чтобы не упасть на
полях, которых нет в описании.

**Альтернативы.**
- Жёсткая схема наугад: гарантированно сломает реальный `taxonomy.json` после доставки.
- Без схемы вовсе: не работает CI на старте.

**Последствия.** При доставке реального `taxonomy.json`:
1. Прогнать `validate_taxonomy.py` — посмотреть, что пропустила схема.
2. Дополнить схему недостающими обязательными полями.
3. Возможно ужесточить `additionalProperties`.
4. Зафиксировать новым ADR со ссылкой «supersedes ADR-005».
